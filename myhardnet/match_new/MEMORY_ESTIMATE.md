# HardNet 匹配单 query 增量内存估算

## 结论

在当前配置、CPU + ONNX Runtime、256 bit packed Hamming 描述子、每个身份 20 个注册模板、query 原始灰度图已经位于内存且不计图像读取的前提下：

- **仅执行已经生成好的 query 模板与一个身份的 20 个注册模板匹配**：实测 RSS 峰值增量约 **0.7–0.8 MiB**，USS 峰值增量约 **0.25–0.36 MiB**。这是最接近纯匹配器的增量，生产可按 **1–2 MiB** 预留。
- **从 query 图像生成模板并匹配，而且请求路径已经完整预热**：实测稳定请求的增量约 **1–3 MiB**。这里包括 SIFT、patch 提取、HardNet 推理、Hadamard 二值化和 1:1 匹配，但不包括 query 图像读取。
- **只有模型做过一次推理预热、完整 query 路径尚未预热**：第一次实际请求通常观测到约 **7–12 MiB** 的进程 RSS/USS 增长。建议至少按 **15 MiB/并发 query** 规划普通请求临时内存。
- **运行时分配器或 ONNX Runtime 在后续请求中首次扩容**：本机还观察到一次约 **87–92 MiB** 的额外高水位增长。它属于一次性的运行时/分配器工作区扩容，不是每个 query 的算法对象大小；如果服务不做完整路径预热，应按 **约 100 MiB 的一次性进程增长余量** 规划，或者在启动阶段主动完成多次真实 query 预热。

因此，针对用户指定的口径，最实用的答案是：

> **纯匹配阶段约 1 MiB；把原始 query 图像的特征提取和 HardNet 推理也计入后，完整预热后的单 query 稳态增量约 1–3 MiB，生产建议按 15 MiB/并发 query 预留。若只预热模型而不预热完整请求路径，还要为运行时首次扩容额外预留约 100 MiB 的进程级安全空间。**

模板库本身已经按要求排除，不计入上述增量。

## 测量口径

- 操作系统：当前 Windows 环境。
- Python：3.13.9。
- query 原始图像在请求开始前已经存在于内存，因此测量代码将图像读取替换为已存在的 NumPy 图像；没有把读取图像的内存计入请求增量。
- 当前样本图像尺寸为 `110 × 100`，实际 query 有 324 个关键点；配置上限为 400 个关键点。另一个高关键点样本为 383 个关键点。
- 模型使用 `onnxruntime` CPU 后端，推理批量上限按 400 个 `32 × 32` patch 进行预热。
- 1:1 场景只比较一个已知身份的 20 个注册模板。
- 模板库先加载并完成匹配，之后才记录基线；模板库的常驻内存没有计入增量。
- 采用 Windows 进程 `RSS` 和 `USS`：RSS 是进程驻留集大小，USS 是只属于该进程的物理内存，更适合观察增量。
- 使用约 1 ms 采样间隔记录阶段高水位；结果是进程级高水位，不是单个 Python 对象的精确 `malloc` 大小。

## 实测结果

### 仅匹配阶段

测试条件：query 模板和一个身份的 20 个注册模板均已加载，重复调用 `score_query_against_identity()`。

- RSS 增量：约 `0.67–0.78 MiB`
- USS 增量：约 `0.25–0.36 MiB`
- 单次匹配耗时：约 `10–13 ms`，本机样本
- 20 个模板全部参与匹配；本次记录未依赖身份早停来减少模板数量

当前 CPU Hamming 路径使用 OpenCV 的 `batchDistance` top-k 结果，未构造大型浮点全距离矩阵，所以纯匹配阶段的临时内存很小。

### 包含 query 模板生成

测试条件：query 图像已经在内存，执行 SIFT、patch 提取、HardNet ONNX 推理、Hadamard 二值化、模板组装，然后与 20 个注册模板匹配。

稳定预热后的单身份测试中：

- 第 1 次请求峰值约 `1.65 MiB RSS / 1.64 MiB USS`
- 第 2 次请求峰值约 `2.08 MiB RSS / 2.07 MiB USS`
- 第 3 次请求峰值约 `2.57 MiB RSS / 2.56 MiB USS`
- 这些值包含 Python、NumPy、OpenCV 和 ONNX Runtime 分配器逐步保留的高水位

只对模型做 400 patch 的一次推理预热、但不预热完整 query 构建路径时，多个新进程首次实际请求观测到约 `7–12 MiB` 增长。另一次连续构建测试中，ONNX Runtime/底层分配器在第二次请求发生了约 `86–90 MiB` 的一次性扩容；扩容后后续请求只增加约 `0.3–0.5 MiB`。这也是生产启动阶段应做完整路径预热，而不能只调用一次模型 forward 的原因。

### 模板库大小

当前模板产物中：

- 36 个身份
- 每个身份 20 个模板
- 共 720 个模板
- 平均每个模板约 335 个关键点
- 仅计算已加载 NumPy 数组：约 `20.9 MiB`
- 其中主要数组约为：packed HardNet 描述子 `7.36 MiB`、`overlap_image` `7.55 MiB`、关键点坐标和三个关键点属性数组合计约 `4.60 MiB`
- 一个身份的 20 个模板数组约 `0.59 MiB`

`np.savez_compressed` 只影响磁盘文件大小；调用 `load_image_template()` 后，数组会解压为内存中的 NumPy 数组。

## 代码依据

`run_hardnet_matching.py` 的主流程先构建或复用图像模板，再调用身份级评估；完整离线程序还包含批量评估、CSV/JSON 输出，不应直接等同于生产 1:1 请求服务。

`evaluation.py` 中的 `cache` 是按模板路径缓存且没有淘汰策略。离线评估时它会持续保留不同 query 和 gallery 模板；生产服务若只验证一个已知身份，应使用固定身份的模板缓存或显式限制缓存范围。

每份加载后的模板包含关键点数组、packed HardNet 描述子和 `overlap_image`。当前 110×100 图像的单模板数组理论大小约 30 KiB，其中二值描述子约为 `N × 32` bytes。

query 生成阶段最多会产生 400 个 `32 × 32` 的 FP32 patch；单个完整 patch 数组约 1.56 MiB，但标准化、推理输入、输出和后处理阶段存在多个短生命周期数组。最终进程峰值还受到 native runtime/workspace 和分配器缓存影响。

纹理验证对每个模板比较都会建立仿射后的 query 图像、support mask 和若干 FP32 临时数组。当前图像只有 110×100，因此这些图像级数组本身不是主要峰值来源；如果未来输入图像尺寸显著增大，应重新测量。

## 生产建议

1. 如果 query 前端已经在别的模块完成，只把已生成模板交给匹配器：按 **2 MiB/并发 query** 增量预留。
2. 如果本模块从原始 query 图像开始处理，并且启动阶段完成 SIFT、patch、HardNet、二值化、纹理验证和匹配的完整路径预热：按 **15 MiB/并发 query** 预留，通常足以覆盖当前配置的请求临时内存。
3. 如果只预热模型、不预热完整路径：除并发请求预算外，服务进程还应额外预留 **约 100 MiB 一次性运行时扩容空间**；或者在启动时连续执行若干真实 query，直到 RSS 高水位稳定。
4. 多个并发 query 不能共享各自的 query 图像、patch 和中间数组，应按并发数增加临时内存预算。
5. 模型、ONNX Runtime session 和模板库属于常驻内存，应单独加入服务容量。当前全库 720 模板仅数组理论值约 21 MiB，但完整 Python 进程还包括模型、运行时、线程和对象开销；实际部署应压测。
6. 当前离线 `cache` 无淘汰机制。若把 `run_hardnet_matching.py` 直接长期运行在服务中，query 模板会不断加入缓存，内存会随 query 数量增长；生产接口应显式释放 query 模板或使用有界缓存。
7. 如果改用浮点 L2 描述子、增大关键点上限、增大原图/`overlap_image` 尺寸，或者改为 1:N 全身份识别，应重新测量。浮点 256 维描述子每个关键点约占 1024 bytes，而当前 packed 二值描述子只占 32 bytes。
