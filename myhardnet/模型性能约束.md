# 模型性能约束

用途：保存本项目已经确认的部署性能要求与验收口径，作为后续模型、二值化方式和推理实现的筛选依据。

首次确认日期：2026-10-20；最新修订：2026-10-26。用户确认以“完整识别平均 < 100 ms”取代旧的“描述子生成 p95 < 70 ms”；内存继续使用预热后单请求峰值 RSS 增量口径。最新模型筛选范围放宽为单patch约80 MFLOPs以内、FP32参数净大小约10 MB以内，替代此前“MAC严格低于m1”的结构限制。

## 硬性要求

后续方案必须同时满足以下要求，不能只凭参数量、MACs、权重文件大小或某一段推理耗时判定达标。

- 目标机器：本机 AMD Ryzen 9 5900HX，8 核 16 线程；Windows；Python 3.13.9；CPU FP32 ONNX Runtime 推理环境。
- 工作负载：一张灰度指纹图像，约 400 个有效关键点；本次新模型输出约 400 个 **256-bit** 描述子，每个打包为 32 bytes。
- 模型结构初筛：单个 `1×32×32` patch的Conv/Linear约算 **MFLOPs不超过80左右**，以 `1 MAC=2 FLOPs`、`1 MFLOP=1,000,000 FLOPs` 计；FP32参数净大小 **约10,000,000 bytes以内**，按参数数目乘4计算。参数不包含运行时、激活、工作区和模板。接近边界的模型报告实际数值，不将“左右”自动当作严格阈值或隐藏超出量。
- 时间：充分预热后，从内存中的灰度图像开始，到与指定身份 40 张注册模板完成比较并给出最终判定，完整单次身份验证的**算术平均耗时 < 100 ms**。旧的特征提取 p95 < 70 ms 不再作为独立硬门槛；仍报告尾延迟用于诊断。
- 内存：从请求开始到最终身份判定结束的完整 1:1 识别请求，其峰值 RSS 相对完整识别路径预热后空闲基线的增量 **严格小于 30,000,000 bytes**，即十进制 30 MB，约 28.61 MiB。
- 应用场景：**1:1 指定身份验证，每个身份使用 40 张注册模板**；不能用 1:N 全库检索的工作负载代替这一场景。

2026-10-26 较早提出的“新骨干与输出头总MAC严格小于m1的5,004,288”已被上述80 MFLOPs/10 MB左右的筛选范围替代。原m0浮点256约80.2816 MFLOPs、9.536128 MB，属于约80的边界参考；若后续采用严格`<80.0000 MFLOPs`，它不通过该严格门槛。

本次先按结构预算筛选，再保留完整时间与ΔRSS实测检查。这两种口径相关但不等价：FLOPs不包含检测和40模板匹配，参数字节不包含请求峰值缓冲，不能由“80 MFLOPs/10 MB以内”直接认证“100 ms/30 MB”。统一Conv/Linear计数还不包含归一化、激活、sign、pack等运算。

## 时间测量边界

计时覆盖以下完整路径：

```text
内存中的灰度图像 → 关键点检测 → patch 裁剪 → 标准化 → CNN 描述子前向
                 → 二值化与 bit 打包 → 40 张模板匹配 → 候选筛选
                 → 几何 / 纹理验证 → 身份分数融合与最终判定
```

上述步骤都必须计入同一个请求的识别耗时。单独测量 CNN、二值化、特征提取或匹配，只能用于定位瓶颈，不能作为 100 ms 指标的验收值。主验收遍历全部 40 张模板，不通过省略拒绝路径或仅计接受早停请求降低均值。

用户确认以**已经位于内存中的灰度图像**为起点，因此不包含图像磁盘读取、文件解码与转灰度。采集、上游图像处理与锁体动作不在这一软件识别范围内；若未来产品需要这些步骤，另行计时，不能复用当前结论。请求内部实际启用的检测预处理、mask / quality 获取与适配必须计入并记录。

预热必须运行上述完整路径，并覆盖实际使用的约 400 个 patch 的形状与分批方式。记录实际检测、保留和输出的关键点 / 描述子数量，避免通过显著减少工作量获得达标结果。报告请求数、算术平均、p50、p95、最大值及百分位算法。本人 / 非本人、质量分组分别报告，并提前固定总体样本和权重，不能通过事后改变接受 / 拒绝比例获取有利均值。时间与内存宜分开重复测量，避免 RSS 采样线程干扰计时。

## 内存测量边界

RSS 表示进程当前驻留的物理内存；Windows 测量时应明确采用的工作集 / RSS 采集接口。内存测量覆盖灰度图像请求开始、关键点检测、patch 裁剪、标准化、CNN、二值化打包，随后继续覆盖与指定身份 40 张注册模板的匹配、候选筛选、RANSAC、纹理验证，直到最终身份判定结束。**新口径的时间与内存指标覆盖相同的完整请求范围。** 验收计算为：

```text
baseline_RSS = 包含 40 模板匹配与最终身份判定的完整识别路径充分预热、回到空闲状态后的进程 RSS
peak_RSS     = 单次识别请求开始至最终身份判定结束期间的最高 RSS
ΔRSS         = peak_RSS - baseline_RSS
验收要求     = ΔRSS < 30,000,000 bytes
```

模型、ONNX Runtime 运行时和注册模板已经常驻产生的内存计入 `baseline_RSS`，不重复计入本次请求增量。请求期间新分配或首次驻留的临时数组、patch、激活、中间描述子、打包结果、匹配距离与候选数组、RANSAC 和纹理验证中间结果等，应由全请求峰值采样反映。

必须同时报告以下数值，防止较小的增量掩盖较大的常驻空间：

- 完整路径预热后的绝对 `baseline_RSS`。
- 请求的绝对 `peak_RSS` 和计算出的 `ΔRSS`；内存硬限值按峰值增量判断，不按 p95 内存判断。
- 加载模型 / 运行时 / 模板后的空闲 RSS，以及首次运行完整路径产生的扩容峰值与扩容量。
- 预热次数、最大预热输入形状、内存池 / 缓存行为、RSS 采样方式和采样间隔。

预热形成的常驻内存和首次扩容必须单独呈现，不能隐藏，也不能与单请求增量混为一项。权重文件大小、模型参数字节数和描述子净大小均不能替代实际 `ΔRSS` 测量。

## 对照与验收记录

方案筛选应在上述 AMD 本机环境、相同图像与约 400 个有效 patch 的负载下进行，记录模型 / checkpoint、二值码长、实际执行后端、ONNX Runtime / OpenCV 版本、线程数、batch 与分块配置。若某些算子仍由 PyTorch 等其他后端执行，应明确记录实际混合执行路径。

旧的 Intel i7 基准或其他设备数据只能作为参考，不能认证此 AMD 机器满足约束；理论 MACs、参数量和描述子压缩率也不能代替本机完整路径实测。

每次验收记录应列出上述延迟和内存证据，再给出该配置是否**同时满足**时间与内存要求的结论。本文件先固定要求和测量口径；具体模型的通过 / 失败结论由对应本机实测记录给出。

精度要求：在相同 FAR 下比较最终身份级 FRR，越低越好；暂不固定 FAR 数值，不擅自设定允许的精度回退。不同共同工作点各有优劣时保留对比，不宣称存在无条件最优模型。

历史记录：[模型性能实测](模型性能实测.md)（2026-10-20）。其中时间仅测描述子生成，旧的通过结论不能自动认证新的完整识别平均 < 100 ms。
